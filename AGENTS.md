# AGENTS.md

The single source of truth for coding agents in this repo. Hand-edit this file only — every
tool-specific file (`CLAUDE.md`, `.claude/skills/`) is generated by `pnpm sync:agent` and CI fails
if it drifts.

## What this is

A **Conversation AI Agent Harness** for GoHighLevel. A customer messages a business; GHL fires an
inbound-message webhook; the harness decides what should happen — answer from the business's
knowledge base, run a skill, or hand over to a human — does it, and replies into the same CRM
conversation. Every turn emits a complete trace.

Four things are being graded, and they shape every decision here:

1. **Abstractions** — adding a fourth provider or a third skill must be one new file. Nothing in
   `packages/core` may know that GoHighLevel exists.
2. **Completeness** — the loop closes end to end against a real sandbox, not a mock.
3. **Eval rigor** — negative cases and honest failure reporting, not a demo.
4. **Technical integrity** — a readable orchestration loop, explicit RAG-trigger logic, measured
   latency (p50 ≤ 3s / p95 ≤ 6s webhook-to-send on non-RAG turns).

Anything that hides one of those four behind a framework is the wrong call, even when it saves
time. Plumbing (HTTP, validation, provider message normalization, chunking, queues) is the
opposite: use the standard library for it and move on.

## Where things live

| Box                 | Path                     | Rule                                                                     |
| ------------------- | ------------------------ | ------------------------------------------------------------------------ |
| The harness         | `packages/core`          | The loop, tracing, skill contracts, RAG + gate. **Imports nothing GHL.** |
| CRM client          | `packages/ghl`           | Typed GHL API access, OAuth token lifecycle, SSO, webhook schemas        |
| The three skills    | `packages/skills-ghl`    | `update_contact`, `book_appointment`, `human_handover`                   |
| Operator settings   | `packages/config`        | zod schemas for env (secrets) and the settings file (tunables)           |
| Persistence         | `packages/db`            | Drizzle schema + migrations; one Postgres for state, traces, vectors     |
| HTTP edge           | `apps/server`            | Express: OAuth, webhooks, SSO, queue and workers                         |
| Admin console       | `apps/admin`             | Vue 3 + Vite; reads traces, writes only validated settings               |
| Customer chat       | `apps/chat`              | Vue 3 + Vite; talks to `apps/server` only, never to GHL directly         |
| Evals               | `evals/`                 | `deterministic/` (Vitest, 0/1 facts) and `judge/` (rubric-scored)        |
| Runtime skill docs  | `skills/<name>/SKILL.md` | Behavioural instructions injected into the system prompt                 |
| Coding-agent skills | `agent-skills/`          | Playbooks for you; tool-neutral, PR-reviewable                           |

Dependency direction is enforced by ESLint (`boundaries/element-types`), not by convention:
`core → config` only · `ghl → config` only · `skills-ghl → core, ghl, config` ·
`apps/* → any package` · apps never import each other. Cross-package imports are bare specifiers,
so the rule that actually catches them is `boundaries/external`; `element-types` covers relative
paths. Both matter.

## Commands

```
pnpm verify                                           # the whole gate — run this before "done"
pnpm build | pnpm typecheck | pnpm test               # turbo, all workspaces
pnpm lint                                             # eslint from the root — see note below
pnpm sync:agent [--check]                             # regenerate tool adapters
pnpm slop-check                                       # staged-diff prose rules
pnpm knip                                             # dead code and unused exports
pnpm format                                           # prettier
```

There is deliberately **no `turbo lint` task**. Lint runs once from the repo root, and must stay
that way: the `boundaries` element patterns are relative to the working directory, so a
per-package invocation matches nothing and every architectural rule stops firing while still
reporting success. A green per-package lint is worse than no lint, because it looks like proof.

## Code standards

- TypeScript strict; `any` and `as any` are lint errors. Prefer narrowing over casting.
- **zod at every boundary**: webhook payloads, tool inputs, settings, env, and every external API
  response. Data that entered the process unvalidated may not reach business logic.
- **Every model call and every tool call emits a trace event.** A step that isn't traced didn't
  happen, as far as a reviewer is concerned. New event types go in
  `packages/core/src/tracing/events.ts` first.
- No `console` outside `apps/server/src/logger.ts`. Use the injected logger.
- Configuration over constants: if an operator would plausibly want it different, it belongs in
  `packages/config/src/settings.ts`, not in a literal.
- Files stay under ~300 lines. The loop itself stays under ~120. If a file is growing past that,
  the split is usually already obvious.
- No barrel-file re-export chains beyond each package's single `src/index.ts`.
- New dependency? Add a one-line comment in the PR description saying what it replaces. Reject
  anything that wraps the loop, the providers, the tracing, or the evals.
- Read the types before calling anything. Never invent an API surface.
- **Ask before spending money.** Eval runs, `pnpm bench` and `pnpm kb:ingest` call paid APIs.
  Confirm before running them, so nobody learns what a run cost from a billing page.

## Output contract

These are not style preferences; they are what makes your output reviewable.

- Respond with diffs and files. Not with an essay about the diff.
- End-of-task report: files changed, and gate status. Five lines maximum.
- Comments explain **why**, never **what** and never **what changed**. `// added to fix the 401`
  is archaeology — git has it. `// single-flight: a burst of webhooks would otherwise fire N
refreshes and GHL invalidates all but one` is a reason.
- **Two lines is the ceiling for a comment.** Reasoning that needs more goes in
  `docs/architecture.md` under an anchor, and the comment points at it: `See #connection-pool`.
  Anchors there are load-bearing, so deleting one breaks the comments that reference it.
- **Never document what you have not verified.** Read the file, run the command, check the path
  resolves. A described mechanism that does not exist is worse than no documentation, because it
  costs a reviewer the time to discover it is fiction.
- No emoji anywhere in source, comments, or commit messages.
- **Every commit you author ends with a `Co-Authored-By:` trailer naming the agent that wrote it**
  — whichever tool that is, with its own no-reply address. Attribution stays accurate when the
  tool changes, and `git log --author` remains a straight answer to "what did a human write".
- No dead code, no commented-out code, no placeholder stubs unless a plan explicitly calls for one.
- No drive-by refactors. Surgical diffs. If you spot something unrelated and worth fixing, say so
  in one line at the end instead of doing it.
- No apologies, no restating the task back, no "Here's what I did".
- "Done" means `pnpm lint typecheck test` is green. Never "this should work now".
- If a requirement is ambiguous, implement the reading you can defend and name the assumption in
  one line. Do not stop and ask for anything you could have decided.

## Changing these rules

You may edit this file, and you may add playbooks under `agent-skills/`. Three things follow.

**Regenerate.** After editing this file, run `pnpm sync:agent`. `pnpm verify` runs
`sync:agent --check`, so a stale `CLAUDE.md` fails the build. Never hand-edit `CLAUDE.md`: it is
overwritten on the next sync, and to change what it says beyond the import you edit
`CLAUDE_MD_CONTENT` in `scripts/sync-agent.ts`. Adding a playbook needs no registration:
`.claude/skills` symlinks the whole `agent-skills/` directory, so a new subdirectory with `name` and
`description` frontmatter is discovered on its own.

**Know which of the three you are editing.** They are all markdown and two are called SKILL.md:

| File                      | Governs                                  | Needs eval cases |
| ------------------------- | ---------------------------------------- | ---------------- |
| `AGENTS.md`               | how you write code                       | no               |
| `agent-skills/*/SKILL.md` | how you perform one coding task          | no               |
| `skills/*/SKILL.md`       | what the shipped agent says to customers | **yes**          |

The third is production behaviour. It is injected into the system prompt at runtime, so a wording
change there is a behaviour change and belongs with fixtures that prove it.

**Never relax a rule in the same commit as the work it would have failed.** Propose the change on
its own, with the case that motivated it named, and let a human take it. A gate loosened in the
same breath as the run it blocked is indistinguishable from a gate that was never there, and the
diff cannot tell the reviewer which one happened. If a rule is genuinely wrong, say so in one line
at the end of your report and leave it standing.

## Precedence

On any conflict: this file and `agent-skills/` win over community or third-party skills, which win
over tool defaults. Package-local `AGENTS.md` files override this one within their directory. There
are two, `packages/core/AGENTS.md` and `evals/AGENTS.md`.
